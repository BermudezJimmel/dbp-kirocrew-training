Treat It Like a New Hire

The one frame we'll use for the whole session

  • Job description — what it's there to do (the prompt)
  • Toolbox — what systems it's allowed to touch
  • Boundaries — what needs permission, what's never allowed
Analogy: vague onboarding leaves a new hire guessing. Vague instructions get vague results from an agent too.

Account & Token Management

One login, one shared pool — this surprises most new users

  • Log in once with kiro-cli — no separate Crew account or token
  • Chat and scheduled runs both draw from the same Kiro plan
  • Script / command cron jobs skip the model entirely — zero tokens
A job spends tokens only when the AI model reads or writes something. "Check disk space with df -h" is a plain shell command — Crew runs it, nothing reaches the model, cost is $0. "Summarize today's tickets" needs the model to read and write — that one spends tokens.
Analogy: like a company gas card. Every driver fills up from the same tank — you track who's driving, not the card.

Works While You're Away

Three mechanisms that keep running unattended

⏰

Scheduling

Timezone-aware cron jobs, recurring or one-shot

📋

Task Runner

Hand it a spec; it plans, executes, checkpoints, retries

🔗

Webhooks / Heartbeat

External events, or its own steady pulse, wake a session

  • Spec = the steps you write in a plain file, like a recipe card
  • Checkpoint = saved progress — a resumed run skips finished steps
  • Retry = a failed step runs again on its own before it gives up
  • Webhook = an outside system calls IN — Jira, CI, Slack "hooks" into Crew
  • Heartbeat = Crew wakes ITSELF on a steady pulse, no outside caller needed
Analogy: like hiring a night-shift guard. The office closes, the work doesn't.

The #1 False Assumption

Flag this early — it's the most common misunderstanding in this room

What people assume

  • It already knows our AWS account
  • It can check our systems automatically
  • Capability is automatic

What's actually true

  • Only works if a tool/credential is wired in
  • No tool wired in = generic, non-specific answer
  • Capability is explicit, scoped, least-privilege
Analogy: like a new contractor with no office key yet. They can't open doors you never gave them access to.

Defense in Depth

7 named safeguards, every action audit-logged

  • OS-level sandbox around the agent process
  • Credential redaction on every AI output
  • Signed, machine-pinned dashboard tokens
  • Blocked commands, logged and explained — not just refused
  • Prompt-injection and credential-leak protection
  • Slack access is owner-only, never open
  • Every third-party app load is trust-gated and audited
Analogy: like an airport. Many small checkpoints — together they stop almost everything bad.
Note: Browser and Computer Use control need DBP security sign-off before any demo.

Agent Creation: The Parts

Config, not a new brain — made in Customize → Mates → New Mate

  • Name — how you and Crew both refer to it
  • Workspace — the folder it is allowed to read and write
  • Memory — its OWN saved notebook of what it has learned about you and the work. Not server RAM, not shared with other agents unless you point two at the same one
  • Model — which AI model answers for this agent
Analogy: like writing a job posting. A vague title gets a vague hire — a clear one gets the right agent.

Letting Agents Work Together

One agent can hand work to another — in the background

  • Trigger words — phrases that tell Crew "route this kind of task to me"
  • Route — Crew reads the task, checks every agent's trigger words, picks the best match
  • A "!" phrase blocks that agent — even if it otherwise scored highest
  • One agent can delegate by name to another; the work runs in the background and reports back
Example: your Solutions Architect agent gets "set up a new client." It delegates account setup to Pre-Sales and the onboarding checklist to PM, keeps the architecture work itself — all three run at once, in the background, then report back to it.
Analogy: like a team lead handing out tickets. Everyone works their part at once, not one after another.

Kiro Crew vs Kiro CLI vs Kiro IDE

They ask this every time — have the answer ready

AspectKiro IDEKiro CLIKiro Crew
What it isAI code editorThe terminal AI engine — Crew runs on it tooAlways-on platform built on kiro-cli
Where it runsInside the IDE, per projectOne terminal sessionBackground gateway, 24/7
MemoryPer IDE sessionPer terminal session, localPersistent, shared across sessions
SchedulingNoneNoneCron, webhooks, heartbeat
Multiple agentsNoNoYes — many crew members
Best forWriting & editing codeScripts, CI, quick terminal tasksAutomation that runs without you

Crew doesn't replace the CLI — it wraps it with memory, schedules, and a gateway that never closes.

Analogy: IDE is a workbench. CLI is the engine. Crew bolts that engine into a factory floor that runs around the clock.

Where Your Session Lives

Same question, three different answers

ToolWhere it livesSurvives you closing it?
Kiro IDEIn the project, on your machineYes, if you reopen that project
Kiro CLIOne terminal runNo — unless you resume it
Kiro CrewOn the always-on gatewayYes — keeps running
  • CLI tip: pick up a past run with kiro-cli chat --resume
  • Crew tip: closing the dashboard tab never stops the work
  • IDE "Migrate to cloud": check with your Kiro admin before stating what it does on stage
Analogy: IDE is a desk. CLI is a phone call. Crew is an office that never closes.

Key Takeaways

  • One account funds every request on a shared gateway — plan accordingly
  • Crew works unattended, but only has the capability you explicitly wire in
  • An agent is a job description + toolbox + boundaries, same as onboarding a hire
